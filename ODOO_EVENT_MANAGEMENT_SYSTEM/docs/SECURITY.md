# Security Baseline

## Authorization model

* Two groups, both attached to the `res.groups.privilege` "Event Management
  System": **EMS User** (implies `event.group_event_user`) and **EMS
  Administrator** (implies EMS User and `event.group_event_manager`).
* Explicit ACLs for every EMS model. Portal users get read-only access to
  `ems.ticket` and nothing else.
* Three layers of record rules, applied uniformly:
  1. a **global** company rule confining records to the user's activated
     companies;
  2. a **modification** rule (`perm_read = False`) confining write/create/unlink
     to the event's organizer — read stays open within the company so gate
     staff can scan events they do not own;
  3. a **widening** rule for EMS Administrators, because non-global rules are
     OR-ed across a user's groups.
* Portal attendees are confined to `partner_id = user.partner_id` on
  `ems.ticket`, and the portal controllers additionally re-resolve every ticket
  through a partner-scoped domain rather than trusting the rule alone.

## Access credentials (QR envelopes)

* Short-lived HMAC-SHA256 envelopes: TTL clamped to 15–300 s, carrying the
  ticket UID, token version, event id, issue time, expiry and a nonce.
* Signatures compared with `hmac.compare_digest`.
* The signing key lives in `ir.config_parameter` under
  `ems.ticket_qr_secret`. Nothing is committed: a random 48-byte key is
  generated by `ems_ticketing`'s post-install hook. Rotating it invalidates
  every outstanding envelope.
* `token_version` gives per-ticket revocation: revoke, rotate and transfer all
  bump it, so previously issued envelopes stop validating immediately.
* The envelope never appears in a URL, a query string or the page HTML. The
  portal serves it only as the body of a PNG from
  `/my/ems/ticket/<uid>/qr.png`, with `Cache-Control: no-store`.

## Check-in

* Idempotency is keyed on `(device_id, client_scan_uid)` — per device, because
  scanners mint their own UIDs and a global key would silently discard real
  scans.
* The ticket row is locked with `SELECT … FOR UPDATE` before the state
  decision, so two gates scanning the same code concurrently produce exactly
  one `accepted` and one `duplicate`.
* The whole evaluation runs in a savepoint; a losing race on the unique index
  returns the winner's log instead of failing.
* Replay is bounded by three independent mechanisms: envelope expiry, the
  terminal `used` state, and `token_version`.
* Device authorization is independent of user authorization: enrollment issues
  a random secret and stores only a PBKDF2-SHA256 hash (200 000 rounds,
  per-device salt) in administrator-only columns. A stolen operator credential
  on an unenrolled device cannot post check-ins.
* Revoked devices still resolve, so their attempts are recorded as
  `device_revoked` rather than vanishing.

## API surface

* No public, unauthenticated mutation endpoint exists.
* `/ems/api/v1/*` uses `auth='bearer'` for API-key clients.
* `/ems/scanner/api/*` uses `auth='user'` for the bundled PWA, because Odoo 19
  accepts a session on a bearer route only for top-level document navigations
  (see `DEPENDENCY_VERIFICATION.md`). Both families share one authorization
  path.
* No route sets `cors`; everything is same-origin.
* CSRF stays enabled for HTTP form routes. JSON-RPC routes rely on
  authenticated sessions or API keys plus server-side authorization.
* Model methods reachable from controllers (`validate_envelope`,
  `sync_offline_batch`) re-check the caller's group themselves.

## Use of `sudo()`

Every elevation is narrow, deliberate and commented at the call site:

| Where | Why |
| --- | --- |
| `ems.ticket._qr_secret` | reads the signing key, which no EMS user may read directly |
| `ems.scan.log._evaluate` | applies the check-in state change; gate staff hold read-only rights on tickets of events they do not organize |
| `ems.scan.log.validate_envelope` | writes `device.last_seen_at`; widening the device ACL would permit device tampering |
| `ems.scanner.device._verify_secret` | reads the administrator-only hash columns to verify a presented secret |
| `ems_gdpr.action_anonymize` | an EMS administrator is not automatically a contacts manager, but erasure is their job; scoped to one partner after `_ensure_officer` |
| `ems_website` portal controller | reads four scalar event fields for display; portal users cannot read `event.event` |
| `ems.waitlist.entry.action_accept` | creates the resulting `event.registration` |

Group guards short-circuit on `env.su` so scheduled actions and deliberate
`sudo()` paths work, while ordinary users are still checked.

## Payments

* EMS never contacts Stripe. Odoo's `payment` / `payment_stripe` modules own
  the provider lifecycle; EMS reacts to `_set_done` / `_set_canceled`.
* No PAN, CVC or any card data is stored, logged or exported. EMS keeps only
  the `payment.transaction` reference.

## Data protection

* Subject-access export covers registrations, tickets, badges, waitlist entries
  and check-ins, and deliberately excludes signing material, device secrets and
  ticket UIDs. A test asserts the signing secret never appears in an export.
* Anonymization scrubs direct identifiers while preserving referential
  integrity, and refuses to run while the contact holds active tickets.
* **Legal hold** blocks both anonymization and retention purging. A refused
  erasure is recorded as `rejected` with a reason rather than raised, so the
  refusal survives in the audit trail.
* Retention purges check-in telemetry older than
  `ems.gdpr.scan_log_retention_days` (default 730; `0` disables purging),
  always skipping records under legal hold.

## Deployment

* Odoo binds to `127.0.0.1` only; host Nginx is the sole entry point.
* PostgreSQL publishes no host port.
* `list_db = False` and `dbfilter` pinned to the single served database.
* TLS 1.2/1.3, HSTS, `X-Content-Type-Options`, `Referrer-Policy`.
* `render-config.sh` refuses to render while any secret is still `CHANGE_ME`,
  and writes the rendered config `0600`.
* `restore.sh` refuses a backup without a verified checksum sidecar.
* No secret is committed; `tools/validate_package.py` and
  `deploy/scripts/validate-stack.sh` both scan for live keys.

## Known residual risks

* `ems_ai` posts event text to an administrator-configured endpoint. It is
  disabled by default, requires explicit configuration, and can never authorize
  access or payments. Operators should point it only at an endpoint they trust.
* The scanner's device secret is held in the browser's `localStorage`. It is
  scoped to one device and revocable by re-enrolling, but a compromised handset
  should have its device archived.
